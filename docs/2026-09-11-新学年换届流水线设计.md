# 新学年换届流水线设计（2026 版）

> 2026-09-11 · 衔接并取代《2026-09-10-班级管理批量化与换届优化方案》中 P3 的交互设计部分
> 结论先行：**换届 = 一条向导流水线（建学年 → Excel 上传 → 教室绑定批量确认 → 单事务执行），班级端零操作自动切换（无回退，出错由教务端修正重发），旧学年逻辑归档。** 零表结构迁移。

---

## 1. 背景与现状

2026-09-10 那轮已落地：快速建校（`QuickSchoolSetupModal`）、克隆学年结构（`CloneYearModal`）、批量加班、整校名册导入（`StudentImportDialog` 整校模式 + `autoCreateDirectory`）、换届向导（`RolloverWizardModal`，克隆+升班模型，dry-run 单事务）、班级端 `client_switch_binding` + 「待换届」手动横幅。

实际使用后暴露的问题：

| 痛点 | 现状 |
|------|------|
| 流程散装 | 建学年、名单导入、教室重绑分属 3 个独立弹窗，换届要走完需要来回切换多个入口 |
| 名单来源错位 | 换届向导走「克隆+自动升班」模型，而学校每年 8 月拿到的权威数据本来就是新生名册 Excel，自动升班结果还要再人工对一遍 |
| 教室重绑无批量确认 | 换届向导内嵌重绑预览，但没有「全选接受 + 冲突仲裁」的批量确认交互 |
| 班级端手动切 | 每间教室开学要点一次横幅，几十间教室 = 几十次人工操作 |
| 归档为零 | 全库无 archive 概念，旧学年与新学年混在筛选器里 |

**2026-09-11 用户决策（三条，覆盖原方案相应条款）：**

1. **名单来源：Excel 上传为主**——不做自动升班，新学年名册完全来自上传的整校 Excel。
2. **班级端：自动切换，不提供回退**——出错时由教务端在换届执行记录页一键修正重发（原「回退+闩锁」方案废弃，理由见 §5）。
3. **归档：逻辑归档**——数据不动，UI 收纳 + .sch 快照导出。

## 2. 总体流程

```
教务端向导（一条流水线）                既有局域网同步              班级端
┌─────────────────────────────┐
│ ① 建新学年（名称/日期自动顺延） │
│ ② 上传整校 Excel → dry-run    │
│    预览目录 diff + 名册四象限  │──sync_flush──▶ /api/v1/directory ──▶ apply 快照
│ ③ 教室绑定建议 → 批量确认      │   (快照携带 current_school_year_id)
│ ④ 执行（快照备份→单事务）      │                                   ┌──────────────┐
└─────────────────────────────┘                                   │ 自动切换守护：  │
        执行事务内写入 app_settings.current_school_year_id ──────▶ │ 三条件满足即切 │
        旧学年原地保留 = 逻辑归档                                   └──────────────┘
```

## 3. 教务端：换届向导（4 步 Stepper）

入口：「班级与学年」页顶部新增**「新学年换届」主按钮**。快速建校 / 整校导入等独立入口保留（服务非换届场景），向导内复用其解析与落库能力。

### 3.1 Step ① 建新学年

- 名称自动推荐 `20XX-20XX学年`、起止日期顺延一年，一步确认。
- 本步只生成向导上下文，**不落库**——正式写入在第 ④ 步事务内（中途放弃零残留）。

### 3.2 Step ② 上传整校 Excel（权威来源）

- 模板列：`年级 / 班级 / 学号 / 姓名 / 座位号(可选)`；提供整校换届模板下载。
- 解析后 **dry-run 预览**（不写库）：
  - **目录 diff**：Excel 有而系统无的年级/班级 → 列出「将新增 X 个年级 / Y 个班级」；系统有而 Excel 无 → 标记「未涉及，保留原样」。
  - **名册四象限**：沿用整校导入的 diff（新增 / 换班 / 更新 / 缺失），缺失学生仅提示、不静默删除。
  - **错误行报告**：重名、缺班级归属、座位冲突等列明细，支持下载 CSV；存在错误行时禁止进入下一步（不允许静默丢弃）。

### 3.3 Step ③ 教室绑定批量确认

- 系统自动生成**绑定建议**：旧学年 `classroom_assignments` 的每间教室，按名称匹配 Excel 中的新学年班级（如 `三年级2班` → 新学年 `三年级2班`；升年级场景 Excel 中班级名已带新年级）。
- 预览表：`教室 / 旧绑定 / 新绑定建议 / 匹配方式(自动·冲突·未匹配)`。
- 交互：**「全部接受」一键批量确认 + 行内下拉微调**；仅两类情况强制逐行仲裁——多教室映射同一班级、教室无任何候选匹配。未匹配教室可选「暂不绑定」（教室保留，班级端继续用旧绑定，不阻断换届）。

### 3.4 Step ④ 执行

1. **单事务**完成：建学年 → 目录生成（年级/班级）→ 名册落位（显式列名 + `.bind()` 链逐一对齐，SQLx 绑定铁律）→ 写入新学年 `classroom_assignments` → 写入 `app_settings.current_school_year_id`（权威年）。
2. 执行后 `sync_flush`。教室绑定变更不进 `pending_queue`（entity_type CHECK 不含 classroom_assignment，不做表结构手术），由班级端拉目录快照消化（沿用 2026-09-10 方案 §7.4 既定偏差）。
3. 收尾页：换届摘要报告 + 「导出上学年 .sch 快照」一键操作（`package_export_sch` 现成机制；v1 为手动导出，执行前自动快照列为后续增强——自动路径需要静默写盘，本轮不做）+ 「查看执行记录」入口（见 §6）。

### 3.5 初始化模式：第一次使用快速建校（同一向导的空校变体）

教务端首次使用时，SetupWizard（身份/密钥/教室机基础项）完成后引导进入本向导的**初始化模式**，形成「开箱 → 可上课」闭环。与换届模式共用同一条流水线，差异点：

| 步骤 | 换届模式 | 初始化模式（空校） |
|------|----------|--------------------|
| ① 建新学年 | 名称/日期从旧学年版顺延推荐 | 仅输入学年名称（无源学年可推） |
| ② Excel 上传 | 目录 diff 相对旧学年 | 目录 diff 相对空库 → 「将新增全部年级/班级」；命令零改动（`rollover_from_excel` 的 diff 基线本来就是当前目录） |
| ③ 教室绑定 | 按旧绑定自动建议 | 无旧绑定依据 → **v1 整步跳过**：班级端 `classroomClaim` 认领机制现成，设备认领后在执行记录页补绑（教室名单批量录入 + 同名自动绑定列为后续增强） |
| ④ 执行 | 执行后旧学年归档 | 不适用归档；其余一致（单事务、写权威年、sync_flush、收尾页快照导出） |

- 无 Excel 时的降级路径：初始化模式额外保留「手动输入 起止年级 × 每级班数 × 命名模板」批量生成（吸收 `QuickSchoolSetupModal` 的职责，该入口后续可收编移除）。
- 入口补一处：SetupWizard 完成页「下一步：导入全校数据」按钮 → 直接进入向导初始化模式。



新增（均遵循扁平 camelCase 参数约定）：

```
rollover_from_excel(dryRun, schoolYearName, startDate?, endDate?, rows[]) -> RolloverPreview
rollover_from_excel(dryRun=false, ...) -> RolloverResult        // 单事务执行

RolloverPreview {
  newYear: { schoolYearId? }            // dry-run 阶段为占位
  directoryDiff: { newGrades[], newClasses[], untouched[] }
  rosterDiff: { added[], moved[], updated[], missing[] }
  errors: RolloverRowError[]            // 错误行明细
  bindingSuggestions: { deviceId?, classroomId, roomName, oldClass, suggestedClass, match: 'auto'|'conflict'|'none' }[]
}

rollover_rebind(classroomId, classId)   // 修正重发：改写 classroom_assignments + sync_flush
```

修改：

- 目录快照响应（`/api/v1/directory`）附加 `currentSchoolYearId` 字段——服务端从 `app_settings` 读出附带，零新增实体、零新命令。
- `app_settings` 拆为**两个键**（kv 存储，零迁移）：
  - `current_school_year_id`——**权威当前学年**，仅由换届第 ④ 步事务写入；驱动班级端自动切换闸门与归档分组。教务端手动切视图**不得**写此键。
  - `selected_school_year_id`——教务端本地视图筛选（对齐 2026-09-11 已冻结的「教务端切换学年」设计；该设计中原拟用的 `current_school_year_id` 键更名为此，避免与权威年语义冲突）。
  - 两者解耦后：教务端视图停在哪个学年（含换届后不自动联动视图，沿袭冻结决策）不影响班级端自动切换与归档判断。

## 5. 班级端：自动切换（无回退）

### 5.1 切换守护逻辑

apply 目录快照后检测，**三条件全部满足即自动调 `client_switch_binding`（已实现命令）**：

1. 快照携带的 `currentSchoolYearId` 存在且 ≠ 本机绑定学年（教务端没执行完第 ④ 步就永远不会触发）；
2. 本机 deviceId 对应教室在新学年存在 `classroom_assignment`；
3. 目标班级本地名册非空（空则显示「名册同步中」空态，等待下次快照再试）。

守护比较的是**目标绑定二元组 `(schoolYearId, classId)` 与本机绑定是否一致**，而非仅比较学年——这样教务端 §6 的修正重发（同学年内改绑班级）也能自动重新生效，无需班级端任何新逻辑。

### 5.2 为什么不提供班级端回退

- 自动切换的信任链是「教务端 Excel + 名称自动匹配」，出错场景真实存在（绑错班、名册落错位）。
- 原设想的「本机回退 + 闩锁」有一个结构性缺陷：回退后本机状态与权威流（`current_school_year_id`）背离，闩锁机制复杂且留下长期双轨窗口。
- 教务端局域网几乎实时可达，修正重发的恢复路径足够快，且**恢复动作收敛在权威侧**，逻辑更简单、不出现状态背离。

### 5.3 UI

- 自动切换成功后横幅提示：`已切换到 2026-2027学年 · 三年级2班 · 名册 45 人`，提供「知道了」按钮；点击关闭或 24 小时未交互自动收起。**不做永久常驻**——长期信息由状态栏既有的「当前学年 · 班级」承载。
- 原「待换届 → 点击切换」手动横幅删除（被自动切换取代）。

## 6. 教务端：执行记录页与修正重发

- 向导收尾页 / 「班级与学年」页可进入**「换届执行记录」**：展示最近一次换届的摘要（源学年 → 新学年、目录新增数、名册四象限计数、教室绑定结果表）。
- 换届执行在事务内写一条持久审计记录（沿用 2026-09-10 方案的 import_batches 式审计；若现实现未落库审计，则新增 `rollover_executions` 表 + `rollover_execution_details`，均为 `CREATE TABLE IF NOT EXISTS`，零 ALTER 风险）。
- 修正重发：执行记录中任一「教室 → 班级」绑定可下拉改选 → 调 `rollover_rebind` 改写 `classroom_assignments` + `sync_flush`。班级端下次拉快照即按 §5.1 守护逻辑自动重新对齐，全链路无人工干预。

## 7. 归档（逻辑归档，数据不动）

- 换届完成后旧学年**原地保留**，归档语义由**权威年** `current_school_year_id` 推导（见 §4 双键说明），不加新列、零迁移：
  - 所有按学年筛选的页面默认 = 当前学年；
  - 学年选择器中非当前学年归入「历史学年」分组，带归档徽标。
- 历史任务/考勤回看沿用已定口径（ended 任务按 `task_records` 反查学生，不按当前班级过滤，见 2026-09-10 方案 §5.1）。
- .sch 快照导出为收尾页可选操作（`package_export_sch` 现成），仅作离线留存，不触发任何数据清理。

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| Excel 数据质量差 | dry-run 错误行报告 + 存在错误禁止推进；无静默丢弃 |
| 名称匹配错绑 | 绑定建议标明匹配方式；冲突/未匹配强制人工仲裁 |
| 自动切换误触发 | 三条件闸门；教务端未确认换届（无 current_school_year_id）时永不触发 |
| 换届误操作毁数据 | 单事务整体回滚 + 收尾页 .sch 快照导出 |
| 批量插入同步风暴 | 目录走快照全量拉取，天然幂等；名册沿用 batchId 聚合 |
| 修正重发与教学冲突 | rebind 仅改绑定不改名册；班级端守护自动对齐，无并发写冲突 |

## 9. 改动清单与验收

| 层 | 改动 |
|----|------|
| 迁移 | **零**（current_school_year 存 app_settings；审计表如需补则为纯 CREATE） |
| Rust | `rollover_from_excel` 两段式命令 + repo（初始化模式零改动复用）；`rollover_rebind`；directory 快照附 `currentSchoolYearId`；换届审计落库 |
| 教务端前端 | 4 步换届 Stepper（复用整校导入解析；含初始化/换届双模式）；绑定批量确认表；执行记录页 + 修正重发；学年选择器历史分组；SetupWizard 完成页引导入口 |
| 班级端 | 目录 apply 后自动切换守护；横幅改为事件性提示；删除手动切换横幅 |

验收标准：

1. 一所 6 年级 × 4 班、每班 ≤ 50 人的学校：换届 = 上传 1 份 Excel + 全选接受绑定 + 1 次确认，全程 ≤ 5 分钟；
2. dry-run 预览与实跑结果完全一致；中断/失败零残留（学年未建、无脏数据）；
3. 换届执行后，教室端在下次目录同步内**零操作**切到新学年；名册未就绪的教室不切换且有空态提示；
4. 教务端执行记录页修正一个绑定后，对应教室端在下次同步内自动对齐，无需教室端操作；
5. 换届后打开任一历史学年已结束任务，名单与换届前完全一致（含毕业生、转出者）。

## 10. 明确不做

- 自动升班模型（Excel 上传为主，用户决策）；
- 班级端回退 / 闩锁（用户决策，恢复动作收敛在教务端）;
- 物理归档（移出主库）——列为远期选项，需时按表重建铁律另行设计；
- 毕业生 `graduated` 状态（students 表结构手术，沿袭 2026-09-10 §7.4 决策，毕业生原地保留在旧学年班级，新学年名册天然不含）。
