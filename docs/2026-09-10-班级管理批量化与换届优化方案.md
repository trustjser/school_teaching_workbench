# 班级管理批量化与「换届」优化方案

> 2026-09-10 · 教务端 `GradeClassManage` / `StudentImportDialog` 改进提案
> 结论先行：**三个功能、三期落地——① 目录批量生成器 ② 整校名册导入 ③ 学年换届向导（核心）**。零表结构迁移，全部能力建立在现有数据模型上。

---

## 1. 现状诊断（代码级）

| 痛点 | 代码事实 | 后果 |
|------|----------|------|
| 目录创建一次一个 | `GradeClassManage.tsx` 中年级/班级/学年各有独立 Modal，`saveClass` 每次只落一条 `class_upsert` | 建一所「6 年级 × 4 班」的学校 = 1 学年 + 6 年级 + 24 班，**31 次弹窗交互** |
| 学生导入锁死在单班上下文 | `StudentImportDialog` 强依赖 `classContext.classId`，必须先选年级→选班→再导入 | 整校初始化要循环「选班→导入」24+ 次；Excel 里的年级/班级列被忽略，不能反向建目录 |
| 换届零支持 | 换学年 = 手工新增学年 → 逐班重建 → 逐班重新导入名册 | 每年 8 月的例行工作变成半天以上的机械劳动 |
| 学年只是筛选器 | `selectedSchoolYearId` 是 UI 态；班级靠 `school_year_id` 隔离 | 没有「当前学年」的全局语义，换届没有可依托的锚点 |

**关键判断：数据模型其实已经为换届准备好了**——`classes.school_year_id`（年隔离）+ `classes.grade_id`（年级维度）+ `students.class_id`（名册落位）+ `classroom_assignments`（教室×学年×班级）。缺的只是操作层，不是模型层。

## 2. 外部调研（主流做法）

| 产品 | 换届/建目录方式 | 可借鉴点 |
|------|----------------|----------|
| 钉钉家校 | 年级一键「升班」+ 可设**自动升班日期**；新建年级 = 入学年份 + 班级数量，批量生成 N 班 | 「一键升班 + 自动日期」体验最好；班数批量生成 |
| 动易综合素质系统 | 占位符 + 起止序号批量加班；年级设「毕业状态」级联学生毕业 | 占位符命名；年级级联毕业 |
| 云校园 | 学段→年级→班数三层批量建；升班/毕业/分班走 Excel 模板 | Excel 模板做批量异动的兜底通道 |
| ischool（台湾） | 换届 = 毕业班删除 → **高到低逐级改名** → 新生班导入 | 提醒：逐级改名是危险操作，我们的「新学年克隆」模型更安全（旧数据天然保留） |

共性结论：**头部产品都把「升班/换届」做成一个原子向导，而不是让用户手工重建目录**；批量建目录的标准交互是「年级数 × 每级班数」或「占位符 + 序号」。

## 3. 候选方向与取舍

- **方向 A：纯 Excel 全家桶**（导出目录→Excel 改→导回）。灵活但繁琐，是把成本转嫁给用户，不推荐作为主路径；仅保留「学生批量异动」Excel 兜底（现有导入已具备雏形）。
- **方向 B：换届向导 + 批量生成器**（推荐）。一键升班（钉钉模式）+ 新学年克隆班级结构。安全性好：旧学年数据天然保留，新学年是「新副本」，出问题可整体回滚。
- **方向 C：年级按「入学年份」建模、年级名自动推算**（如 2024 级→自动变五年级）。模型最优雅，但要重构 `grade_name` 语义并波及考勤/任务/统计所有冗余字段，**成本远超收益**，列为远期选项，本轮不做。

## 4. 推荐方案：三期落地

### P1 目录批量生成器（低风险，先摘果子）

入口：`GradeClassManage` 顶部新增「快速建校」按钮。

- **快速建校向导**：输入 起止年级（如 一年级~六年级）+ 每级班数（如 4）+ 命名模式（`{年级}{序号}班`，可自定义模板如 `{年级}({序号})班`）→ 预览生成树 → 一键写入。学年可顺带创建（名称自动推荐 `20XX-20XX学年`）。
- **班级批量追加**：在某年级下支持「批量加 N 个班」，自动续接现有 `classNo`。
- **复用上一学年结构**：新建学年后，一键克隆某学年的 年级→班级 结构（不拷学生），班主任留空待填。

技术落点：Rust 新增 `directory_batch_create` 命令（单事务，显式列名 + `.bind()` 链逐一对齐——遵守既有 SQLx 绑定铁律）；目录变更已走 `pending_queue`，批量操作用 `batchId` 聚合下发（`PendingQueueItem.batchId` 字段现成）。

### P2 整校名册导入（解锁 Excel 的目录能力）

把 `StudentImportDialog` 从「单班上下文」解耦：

- 无 `classContext` 时进入「整校模式」：Excel 中的 年级/班级 列参与落位——按 `(schoolYearId, gradeName, className)` 匹配已有班级，**不存在时按预览中用户勾选自动创建**（目录创建也进预览 diff：将新增 X 个年级 / Y 个班级）。
- 保留现有 roster diff（新增/转班/更新/缺失四象限）与单事务回滚。
- 「名单缺失」学生可选处理：标记 `transferred`（转出）或保留，不做静默删除。

技术落点：`student_batch_import` 命令扩展 `autoCreateDirectory: bool` 参数；`classContext` 改为可空。前端模板增加整校版模板下载。

### P3 学年换届向导（核心价值，压轴做）

入口：学年选择器旁新增「开始换届」按钮（仅对「当前学年」可点，需先落 `current_school_year` 语义——存 `app_settings` 即可，不动表结构）。

向导流程（对应下图）：

1. **选源学年** → 自动推荐新学年名（`2026-2027学年`）、起止日期顺延一年。
2. **克隆目录**：复制源学年全部班级（`classNo`/`sortOrder`/班主任保留），年级不复制（年级是全校维度）。
3. **学生升级预览（dry-run）**：
   - 非毕业班：`grade +1`、`className` 随新班级改名、`classId` 指向新学年班级；座位号保留；
   - 毕业班：学生 `status → graduated`、`statusSince` 落时间；
   - 预览界面允许人工微调：留级（不动）、跳级、个别转班——逐行可改；
   - 输出差异报告：升级 N 人 / 毕业 M 人 / 留级 K 人 / 新班级 Z 个。
4. **教室重绑预览**：`classroom_assignments` 按新学年把教室指到新班级（教室物理不变，一教室一班级逐一映射，冲突时人工仲裁）。
5. **确认执行**：整个换届在**单一事务**内完成（任一步失败整体回滚），写 `import_batches` 式审计记录；执行后触发 `sync_flush`，班级端收到目录后只切 `boundClassId` 绑定、不重装（既有跨年切换机制已支持）。

技术落点：Rust 新增 `school_year_rollover(dry_run: bool)` 命令——干跑返回预览报告，确认后带 `dry_run=false` 落事务。结构手术不涉及 `ALTER TABLE`，规避 SQLite < 3.35 迁移坑；对 `pending_queue` 只做 INSERT，不碰表结构。

## 5. 风险与对策

| 风险 | 对策 |
|------|------|
| 换届误操作毁数据 | dry-run 预览 + 单事务 + 执行前自动 `package_export_sch` 快照（.sch 离线包机制现成） |
| 批量插入触发同步风暴 | `batchId` 聚合 + 队列合并；班级端消费幂等（按 entityId upsert） |
| 学生 `grade/className` 冗余字段漂移 | 换届事务内同步改写冗余列，避免考勤/统计视图按旧名聚合 |
| 绑定顺序竞态 | 班级端只在收到新学年目录且 `boundClassId` 存在时才切绑，UI 明确提示「待换届」状态 |

### 5.1 历史任务可回看性（换届视图口径，P3 必含项）

问题：换届后，之前任务的名单还能看吗？

- **数据层：能。** `task_records` 按 `(task_id, student_id)` 落库，换届事务**只改学生与目录，不碰 task_records、不删学生**（毕业生仅置 `status='graduated'`），原始打分/备注 100% 保留。
- **视图层：现状有坑。** 两处查询按「学生**当前**班级」过滤，换届改写 `students.grade/className` 后会错位：
  1. `task_repo::matrix_for_class` —— 学生集合来自 `students WHERE class_name = ?`（回退到任务的 `task.class_name`）。换届后原班学生班级名已 +1，会从矩阵中**消失**；新学年占用该班名的学生反而**顶替出现**。
  2. `task_repo::progress_list` —— scope 匹配走 `s.class_name = t.class_name` / `s.grade = t.grade` 的**当前值 JOIN**，历史任务的按班聚合直接断链（total 归零或算到别人头上）。
  3. 矩阵还排除 `status='transferred'`，换届后转出/毕业学生的历史记录也会被隐藏。

**修复方案（零迁移，仅改两处查询口径）**：按任务生命周期分口径——

| 任务状态 | 学生集合口径 |
|----------|--------------|
| 进行中（status='active'） | 维持现状：按当前 `class_name/grade` 过滤（服务日常打卡与实时进度） |
| 已结束（status='ended'） | 改为 `task_records.student_id` **反查**学生实体，忽略班级名/年级/status 过滤——名单 = 当时实际参与的人，姓名学号照常展示 |

落地点：
- `matrix_for_class`：`task.status == 'ended'` 时学生列表改为 `SELECT students ... JOIN task_records tr ON tr.student_id = students.id AND tr.task_id = ?`（去重），绕过 class_name/status 过滤；无任何记录的 ended 任务维持现口径兜底。
- `progress_list`：ended 任务的聚合基数改为按 `task_records` 计数（final/processing/pending 全部从记录侧推导），不再从「当前班级学生 × LEFT JOIN 记录」推导。
- 换届向导验收新增一条：**换届后打开任一学年已结束任务，矩阵名单与换届前完全一致**（含已毕业、已转出学生）。
- 考勤同理自查：`checkin_records` 按 `student_id + checkin_date` 存储不受影响，但若考勤看板按 `students.class_name` 过滤历史日期，需要同样区分「历史日期按记录反查、当日按当前班级」的口径（P3 实施时一并核查 `checkin_class_attendance` / `checkin_exception_students`）。

## 6. 路线与验收

| 期 | 内容 | 验收标准 |
|----|------|----------|
| P1 | 批量生成器 + 克隆结构 | 一所 6×4 学校目录 ≤ 2 次交互建完 |
| P2 | 整校导入 | 一个 Excel 全校名册，含自动建目录，一次导入落位 |
| P3 | 换届向导 | 千人学校换届 ≤ 1 分钟；dry-run 与实跑结果一致；中断可整体回滚 |

建议顺序 P1 → P2 → P3：P1/P2 独立可用且能立刻缓解建校/导入痛点，P3 依赖前两期的目录批量与整校落位能力。

## 7. 班级端需要做什么

结论先行：**P1/P2 班级端零改动；P3 只需一个「换届绑定切换」能力 + 一处 UI 提示**。

### 7.1 不需要做的（靠既有机制天然消化）

| 改动 | 为什么不用做 |
|------|--------------|
| 批量建目录 / 整校导入的 UI 与逻辑 | 全部是教务端职责。产物仍是 `school_year / grade / class / classroom / classroom_assignment` 五种既有实体，班级端 `/api/v1/directory` 拉取快照后 `apply_snapshot` 按 id 幂等 merge 落库，**无新实体类型、无新命令** |
| 名册消费逻辑 | `CheckinPage` / 任务矩阵按 `boundClassId → students.class_id` 查询，目录换血后同一查询路径自动命中新名册 |
| 学生 / 考勤 / 任务数据同步 | 均按 `studentId / classId` 寻址，与学生实体何时同步无关；旧学年历史按日期查询，不受换届影响 |
| 表结构 / 迁移 | 零 ALTER TABLE，班级端 DB 不动 |

### 7.2 需要做的（仅 P3，两件事）

**① 绑定切换命令（Rust，班级端专属）**

现状缺口：`classroomClaim` + `settings_complete_setup` 在首次配置时把 `school_year_id / class_id / bound_class_id` 一次写死，`SettingsPanel` 明确提示「初始化后不能直接换绑，换绑 = 重置配置重走向导」。方案承诺的「只切绑定、不重装」目前不成立，需要补：

- 新命令 `client_switch_binding(schoolYearId, classId)`：校验 `boundClassId` 存在于本地已同步的 `classes` 且新学年 `classroom_assignments` 中本教室（按本机 `deviceId` 认领关系）确有指向该班级的记录 → 单事务更新 `app_settings` 三个键 → 返回切换后绑定摘要。
- 时序安全：切换前断言本地目录里已有目标班级与新名册（快照是整目录拉取，通常天然满足；不满足时返回「目录未就绪」错误，UI 提示先刷新目录）。
- 离线可用：绑定信息是本地 settings，教务端不在线也能切（assignment 已随目录同步到本地）。

**② 换届感知 UI（共享 SettingsPanel / 班级端首页）**

- 拉取目录后检测：本教室在新学年（非当前绑定学年）存在 `classroom_assignment` → 显示「待换届」横幅：`新学年 2026-2027 · 三年级二班 · 名册 45 人 已就绪，点击切换`。
- 点击 → ConfirmDialog 展示新绑定摘要 → 确认调 `client_switch_binding` → toast + 状态栏刷新为新年级行。
- 名册未同步完成的兜底：切换成功但 `student_list(classId)` 为空时，CheckinPage 显示「名册同步中」空态而非空白网格。

### 7.3 明确不做

- 班级端**不做**任何换届决策（谁升级、谁毕业、怎么重绑教室）——单向权威流：教务端算好结果 → 目录/assignment 表达 → 班级端只消费与确认切绑。
- 不做自动切换（教学机场景错切风险高，必须人工确认）。
