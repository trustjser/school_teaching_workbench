## 修复 CI：`cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` 报错

**根因**：非版本冲突，而是 src-tauri 的 Rust 代码**从未跑过 rustfmt**。全仓 20 个文件、119 处 diff，清一色是「超 100 列未折行」（默认 max_width=100）+ 少量 import 排序。

**版本对齐结论（重要）**：
- CI 固定用 **Rust 1.77.2**（`.github/workflows/ci.yml` 的 `RUST_TOOLCHAIN` + `dtolnay/rust-toolchain@stable with toolchain 1.77.2`，与 `src-tauri/Cargo.toml` 的 `rust-version = "1.77.2"` 一致）。
- 本机默认是 rustc 1.96.1 / rustfmt **1.9.0**。已 `rustup toolchain install 1.77.2 --profile minimal --component rustfmt` 装上 CI 同款。
- 实测两者对本仓库的**格式化决策完全一致**：`cargo +1.77.2 fmt --check` 与 `cargo fmt --check` 输出逐行相同，唯一差别是 1.9.0 会在 `Diff in <file>` 后多打 ` at line N`。→ 本仓不存在 rustfmt 版本漂移风险，本地用哪个版本格式化都可以。

**执行**：`cargo +1.77.2 fmt --manifest-path src-tauri/Cargo.toml`（按 CI 版本落地）。改动 `20 files changed, 605 insertions(+), 188 deletions(-)`。

**改动性质校验（自创手法，值得复用）**：rustfmt 会新增**行尾逗号**和**闭包体花括号**，所以「去空白比哈希」不能直接判定无语义变化。正确做法是 `tr -d '[:space:],'` 后再逐字符 diff：
```
git show HEAD:$f | tr -d '[:space:],' > /tmp/old.txt
tr -d '[:space:],' < $f > /tmp/new.txt
# 再用 difflib.SequenceMatcher 打 opcodes
```
结果：非空白差异仅两类，均语义等价 —— ① `use` 声明重排（`crate::db::repo::settings_repo` 排到 `crate::db::{...}` 之前；`class_repo` 排到 `classroom_repo` 之前）；② 闭包体加/去花括号（`ok_or_else(|| AppError::...)` → `ok_or_else(|| { AppError::... })`、`.map(|c| (a, b))` → `.map(|c| { (a, b) })`）。**注意：这是 rustfmt 的正常行为，不是 bug，review 时不必惊讶。**

**验证（CI 全绿）**：
- `cargo +1.77.2 fmt --check` ✅ / `cargo fmt --check`（1.9.0）✅
- `cargo check` ✅ 8.4s 零警告
- `cargo clippy --all-targets` ✅ 仅 24 warning（CI 未开 `-D warnings`，通过）
- `cargo test` ✅ **92 passed**（lib 层，11.5s）—— 注意 ci.yml 原注释写「当前无 #[test]」，已过时，本次一并更正
- `npm run typecheck` ✅ / `check:boundaries` ✅ / `check:build-targets` ✅

**改动文件**：
- `src-tauri/src/**` 20 个 .rs（纯格式）
- `package.json`：新增 `fmt` 与 `fmt:check` 两个脚本（与 CI 命令逐字一致），避免以后再靠记忆敲长命令
- `.github/workflows/ci.yml`：仅订正 Cargo test 步骤的过时注释

## 修复 Release 打包失败（run 34746934786，tag 1.0.0 → db7a803）

**现象**：Release workflow 三个 OS（ubuntu-22.04 / windows-latest / macos-latest）**全部**挂在同一个 step「Tauri build (affairs / 教务端)」，失败 step 耗时仅 **10–19 秒**，cargo 缓存 0–4s（冷缓存）。

**排查路径（可复用）**：
1. 日志需鉴权，本机无 gh / token，`api.github.com/.../jobs/{id}/logs` 返回 403「Must have admin rights」。**替代手段**：
   - `GET /repos/{o}/{r}/actions/runs/{id}/jobs` → 逐 job/step 的 conclusion + started_at/completed_at（免费、公开仓库可匿名读）。
   - `GET /repos/{o}/{r}/check-runs/{id}/annotations` → 只给 `Process completed with exit code 1.`。
   - **实测 GitHub 公开仓库的 Actions 原始日志（/logs、/job/{id}/logs、zip 包、/lines）一律 404 或 403，无法匿名获取。**
2. **用耗时定位阶段**是关键手法：`tauri build` 内部顺序 = ① 启动 tauri CLI → ② `cargo metadata`（打印 "Looking up installed tauri packages"）→ ③ `beforeBuildCommand`（= `npm run build:affairs`，本地 tsc 25.8s + vite 32s）→ ④ cargo 编译（本例 5m08s）→ ⑤ 打包 .app/dmg。
   失败 step 只有 10–19s ⇒ **必然发生在 ③ 之前**，直接排除前端与 Rust 编译。
3. 交叉验证：CI workflow 的 **Frontend job 在 CI 里是 success**（`npm ci` + tsc + 双端 vite build 全绿）⇒ 前端在 CI 环境没问题，且 `npm ci` 装的依赖（typescript 5.9.3、rollup 各平台包、@tauri-apps/cli 各平台二进制）都齐全。
4. **最终本地复现定案**：`RUSTUP_TOOLCHAIN=1.77.2 npm run tauri:build:affairs` ⇒ 立刻失败：
   ```
   error: failed to download replaced source registry `crates-io`
   Caused by: failed to parse manifest at `.../idna_adapter-1.2.2/Cargo.toml`
   Caused by: feature `edition2024` is required
     ... not stabilized in this version of Cargo (1.77.2)
   ```

**根因**：CI / release 把工具链钉死在 **Rust 1.77.2**，而 Cargo.lock 的依赖树已经涨到 **MSRV 1.88**：`darling 0.23` / `darling_core` / `darling_macro` / `time 0.3.55` / `time-core 0.1.9` / `time-macros 0.2.32` / `plist 1.10.1` 均声明 `rust-version >= 1.88.0`，且 **40+ 个包是 edition 2024**（光 edition2024 就要求 Cargo ≥ 1.85）。lock 是本地新 cargo（1.96.1）生成的，与钉死的旧工具链脱节。

**权威下限算法（值得复用）**：读 `src-tauri/Cargo.lock` 的 659 个包 → 查 **crates.io 稀疏索引**（`https://index.crates.io/{2}/{ab}/{name}`，路径按名字长度分片：1/2/3 字符有专门前缀规则）拿每个版本的 `rust_version` 字段 → 取最大值。**不要只看本地 `~/.cargo/registry/src/`**，那里只有当前平台用的包，Windows/Linux 专属依赖会漏掉。结论：**659 包全平台最高 MSRV = 1.88.0**。

**修复**（4 处）：
- `.github/workflows/ci.yml`：`RUST_TOOLCHAIN: "1.96.1"`，并把 step 的 `toolchain` 改成 `${{ env.RUST_TOOLCHAIN }}` 收敛单一来源；补注释说明为何不能低于 1.88。
- `.github/workflows/release.yml`：同上（原来两处硬编码 1.77.2）。
- `src-tauri/Cargo.toml`：`rust-version = "1.77.2"` → `"1.88"`，这样过旧工具链会报人话「requires rustc 1.88 or newer」，而不是解析依赖时才抛 `edition2024`。
- 选 1.96.1 的理由：**本机默认工具链就是它，且已在本机完成过 release 编译 + .app 打包**（hmm，见下方验证），CI 与本地同版本可消除 rustfmt/clippy/编译行为差异。
- `cargo +1.96.1 metadata --locked` 通过 ⇒ 改 `rust-version` 不会引起 lock 变动。

**版本判定的一致性（多轮实测）**：rustfmt **1.77.2 / 1.88.0 / 1.9.0(1.96.1) 三版对本仓库格式化决策完全相同**，所以 fmt check 在新旧工具链下都过。

## 第二轮修复：release tag `v1.0.0`（run 34748331452）

**修复效果确认**：三个 OS 都越过了 `npm ci` 进入长时间编译 ⇒ **1.96.1 工具链修复生效**。新暴露的失败点：

| OS | 结果 |
|---|---|
| ubuntu-22.04 | 教务端 497s **成功**、班级端 261s **成功** → 死在 `List bundle output`（exit 2，0.0s） |
| macos-latest | 编译+`.app` 打包走了 592s → 死在 **codesign 证书导入** |
| windows-latest | 635s 后 exit 1（不签名无关，原因见下） |

### A. macOS 签名失败（用户明确不要签名）
```
security: SecKeychainItemImport: One or more parameters passed to a function were not valid.
failed to bundle project: failed codesign application: failed to run command security import: failed to import keychain certificate
```
**根因**：workflow 级 `env:` 里写了 `APPLE_CERTIFICATE: ${{ secrets.APPLE_CERTIFICATE }}` 等 6 个变量。**「未配置的 secret」在 GH Actions 里会展开成空字符串（键存在、值为空），而不是「未设置」**；而 tauri-bundler `macos/sign.rs::keychain()` 的判断是
```rust
if let (Some(cert), Some(pwd)) = (var_os("APPLE_CERTIFICATE"), var_os("APPLE_CERTIFICATE_PASSWORD")) { /* import */ }
```
**没有 `is_empty()`**，于是它走导入分支 → `decode_base64("")` 得到 0 字节 → 写一个空 p12 → `security import <空文件>` → errSecParam。
（原注释「留空则走未签名构建，不阻塞流水线」是错的，害了自己。）
**证据**：对照 CLI 二进制字符串，`APPLE_CERTIFICATE` 出现 2 次、`APPLE_SIGNING_IDENTITY`/`APPLE_CERTIFICATE_PASSWORD` 各 1 次，而 **`WINDOWS_CERTIFICATE`/`WINDOWS_CERTIFICATE_PASSWORD` 出现 0 次** ⇒ Tauri v2 根本不读 Windows 证书环境变量（它用 `bundle.windows.certificateThumbprint` + `signCommand`）。
**修复**：把 6 个 APPLE_* 与 2 个 WINDOWS_* 变量**整个删掉**（本项目不签名），并留注释警告「将来要签名必须只在 macos 步骤内按需注入，不能写回 workflow 级 env」。

### B. Windows MSI（大概率是它）
Tauri 的 WiX 模板用 `Language="!(loc.TauriLanguage)"` + `<Package SummaryCodepage="!(loc.TauriCodepage)"/>`，而 `msi/languages.json` 里 **`en-US → langId 1033 / asciiCode 1252`**、`zh-CN → 2052 / 936`。默认 en-US ⇒ 摘要信息走 **CP1252**，而产品名「教务端」在 CP1252 里无法表示 ⇒ WiX `light.exe` 报字符无法编码（LGHT0311），MSI 生成失败。
**修复**：三份完整配置的 `bundle.windows.wix.language = "zh-CN"`（走 CP936）。**未拿到 Windows 原始日志，此条为推断**，需下次运行验证。

### C. Linux `List bundle output` exit 2
原写法 `ls -R <dir> | head -60`，而 `shell: bash` 在 GitHub 上默认是 **`bash -eo pipefail`** ⇒ 只要 `ls` 返回非 0（GNU ls：目录不存在 / 有读不动的条目 → **2**；SIGPIPE → 141）整步就判失败。纯诊断步骤不该有这种权力。
**修复**：改成 `ls -R > bundle-list.txt 2>&1 || true` 先落盘再 `head`（顺带彻底避开 SIGPIPE），并 `if: always()` 永不判失败；另加一步 `Assert bundles produced`（在真正为 0 时明确报错），避免「job 绿了但 Release 是空的」。
（本地以 `bash -eo pipefail` 跑过这两步：列目录 exit 0；断言在 0 产物时按预期 exit 1。注意本机因沙箱拦 DMG，`*.dmg` 天然为 0，所以本地断言必然失败，属预期。）

### D. 上传范围收窄
原 `files: src-tauri/target/release/bundle/**/*` 会把 deb/rpm/appimage 的**解包目录**、macOS `.app` 的内部文件全当 release 资源（成百上千个）。改为只 glob 装机包本体：`deb/*.deb`、`rpm/*.rpm`、`appimage/*.AppImage`、`msi/*.msi`、`nsis/*.exe`、`dmg/*.dmg`。

### 待确认 / 遗留
- **Windows 失败需原始日志确认**（我能拿到的公开信息只有「step exit 1」）。若确为 MSI，zh-CN 修复即解；若报的是 nsis/下载失败，需另行处理。
- **Linux deb/rpm 包名仍是 `教务端`**（`heck::AsKebabCase` 对纯 CJK 无操作），tauri-bundler 自己拼包不校验 ⇒ CI 会绿但 `dpkg -i`/`rpm -i` 会因非法包名失败。`DebConfig` 无 `name` 字段可覆盖，唯一杠杆是改 `productName` 为 ASCII（会连带把 `.app`/`.dmg`/MSI 显示名也变 ASCII，需产品决策）。**已告知用户，待其决定。**

## 收尾核实（同日补充）

### Windows zh-CN 修复已从「推断」升级为「确定」
不只是猜。做了三件事把它钉死：

1. **实测 WiX 包内容**：下载 `wix314-binaries.zip`（41MB，sha 与 tauri-bundler 的 `WIX_SHA256` 对应）解包统计，**`.wxl` 文件数为 0**，唯一相关文件是 `WixUIExtension.dll`。也就是说 Tauri 不依赖磁盘上的 `WixUI_<culture>.wxl`。
2. **读 tauri-bundler 源码确认机制**：light 的调用参数是 `-cultures:<lang>;en-US` + `-loc <output>/locale.wxl`，而 `locale.wxl` 是**运行时由 `default-locale-strings.xml` 模板生成**的（`__language__`→langId、`__codepage__`→asciiCode、`__productName__`→产品名）。该模板里只有 Tauri 自己的字符串（`LaunchApp` / `DowngradeErrorMessage` / `PathEnvVarFeature` / `InstallAppFeature`），**没有任何 `WixUI*` 键** ⇒ WixUI 对话框字符串由 `WixUIExtension.dll` 提供或回退 en-US。
   ⇒ 结论：**切 zh-CN 不会引出「缺本地化」这个新失败**，只是把数据库代码页从 1252 换成 936。
3. **本地 schema 校验**：`node_modules/@tauri-apps/cli/config.schema.json` 里 `WixConfig.language` 类型为 string/array/map（`WixLanguage` 的 `anyOf` 全是 `string`），故 `"language": "zh-CN"` 是合法配置；具体取值由 `languages.json` 在构建期解析（其中确有 `zh-CN → 2052/936`，不会 panic）。
4. **社区交叉验证**：多篇中文博客/issue 记录同一现象（candle 成功 + light 失败 + 中文产品名），修复方式一致为 `windows.wix.language = "zh-CN"`，并有成功产出 `xxx_0.1.0_x64_zh-CN.msi` 的实例。可佐证。

### 又确认的两条硬事实
- **`--config` 可重复且按顺序 merge**：`tauri build --help` 原文「JSON strings or paths to JSON, JSON5 or TOML files to merge with the default configuration file. Configurations are merged in the order they are provided」。项目 `tauri:dev:*` 已在用（传两个 `--config`）。⇒ 解决 Linux 包名问题可以**只在 Linux 构建时追加一个 ASCII `productName` 覆盖**，不必牺牲 macOS/Windows 的中文显示名。
- **`deb.desktopTemplate` / `rpm.desktopTemplate` 存在**（本地 schema：`DebConfig` 有 `desktopTemplate`，描述为「custom desktop file Handlebars template，可用变量 categories/comment/exec/icon/name」）⇒ 即便为 Debian 包名把 `productName` 改成 ASCII，仍可用自定义模板把 Linux 菜单里的 `Name=` 写回中文，视觉损失可控。
