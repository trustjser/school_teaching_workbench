9. **死信永不恢复的根因与修复**（commit 7e75a1a）—— 一次完整的线上排查，值得记住：
   - 现象：班级端状态栏「死信 5」不消失，5 条全是 `ERR_NET / 当前无在线的教务处端可投递`；同时 devices 表里教务处端明明 online。
   - 排查路径：应用数据目录 `~/Library/Application Support/cn.yipaike.lanworkbench.classroom.dev/lan_workbench.db`（dev 构建带 `.dev` 后缀）→ 查 `pending_queue`（**状态列叫 `status` 不叫 `state`**）→ 关联 `sync_log.error_message`、`devices.status`。
   - 直接原因：`revive_dead_for_online_devices`（worker 每轮开头调用）那条批量 UPDATE 撞唯一索引。`ux_queue_dedup` 是**部分索引**：`ON pending_queue(entity_type, entity_id, op_type, COALESCE(target_device_id,'*')) WHERE deleted_at IS NULL AND status IN ('pending','sending')`。一条进入 `dead` 就离开索引作用域，同键新条目于是能再次入队并同样变 dead → 同键出现多条 dead。唤醒语句一次把两条都改回 pending → `UNIQUE constraint failed: ux_queue_dedup` → **整条语句回滚，所有死信都唤不醒**（一条坏数据毒死一整批）。
   - 修复：三步法（快照选存活名单 → 合并被取代的旧重复条目 → 逐条唤醒）。**必须先用独立读语句定名单**：把 NOT EXISTS 写进 UPDATE 的 WHERE 会被逐行求值，前面的行已改成 pending，判断会随更新漂移。
   - 第二个问题：worker 里是 `let _ = revive_dead_for_online_devices(...)`，错误被**完全吞掉**，所以静默了整整半小时。已改为 `tracing::warn!`。
   - 验证：3 个新测试（重复键不整体失败 / 无在线目标不唤醒 / 显式目标离线不唤醒），修复前重复键那条为红。全量 Rust 52/52。
   - 意外收获：改完正好触发 `tauri dev` 热重编译重启，新二进制在**真实库**上把 5 条死信全部救回（4 条送达转 done、1 条重复项被合并软删），更新时间戳 17:18:10。UI 死信计数归 0。
   - 排查技巧沉淀：`sqlite3 -header -column/-line` 读应用库；在**副本**上试跑 SQL 验证假设（`cp` 到 /tmp 再 UPDATE，不碰实时库）。
